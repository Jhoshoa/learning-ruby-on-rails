# Active Record: Models and Databases

Active Record is the part of Rails that talks to your database. It is called an **ORM** (Object-Relational Mapping), which is a fancy way of saying: "It turns rows in your database into Ruby objects you can work with."

Think of it like this:

- A **table** in your database (like `posts`) becomes a **model** in Ruby (like `Post`)
- A **row** in that table becomes an **object** (one instance of `Post`)
- **Columns** (like `title`, `body`) become **attributes** of that object (`post.title`, `post.body`)

## Creating a Model

Rails has a command for generating models:

```bash
rails generate model Post title:string body:text published:boolean
```

This creates two important things:

1. A **model file** at `app/models/post.rb`
2. A **migration file** in `db/migrate/`

## Migrations: Changing the Database

Migrations are like a diary of changes to your database. They let you create tables, add columns, and change things over time.

### rails generate migration

Use `rails generate migration` (short form: `rails g migration`) when you already have a model and need to modify its table — adding a column, changing a type, adding an index, etc.

Use `rails generate model` (which creates the model file + a migration) only when you are creating a **new** table.

```bash
# New table — use generate model
rails generate model Post title:string body:text

# Existing table — use generate migration
rails generate migration AddAuthorToPosts author:string
rails generate migration AddPublishedToPosts published:boolean
```

Rails reads the migration name and infers the change. `AddAuthorToPosts author:string` tells Rails: "add an `author` column of type string to the `posts` table." The generated migration looks like this:

```ruby
class AddAuthorToPosts < ActiveRecord::Migration[7.0]
  def change
    add_column :posts, :author, :string
  end
end
```

Other common migration examples:

```bash
rails g migration RemoveAuthorFromPosts author:string   # Remove a column
rails g migration AddIndexToPosts title:string          # Add an index
rails g migration ChangeBodyInPosts body:text           # Change a column type
```

Each creates a migration file in `db/migrate/`. Run `rails db:migrate` to apply it.

Here is what the migration looks like:

```ruby
# db/migrate/20240101000001_create_posts.rb
class CreatePosts < ActiveRecord::Migration[7.0]
  def change
    create_table :posts do |t|
      t.string :title
      t.text :body
      t.boolean :published, default: false
      t.timestamps
    end
  end
end
```

To run your migrations and actually change the database:

```bash
rails db:migrate
```

To undo the last migration:

```bash
rails db:rollback
```

### Adding a Column Later

If you forget a column, you can add it later:

```bash
rails generate migration AddAuthorToPosts author:string
```

This creates a migration that adds an `author` column to the posts table. Run `rails db:migrate` to apply it.

## The Model File

Your model file is simple to start:

```ruby
# app/models/post.rb
class Post < ApplicationRecord
end
```

But you will add more to it as your app grows: validations, associations, and custom methods.

## CRUD: Create, Read, Update, Delete

Now for the most useful part — working with your data.

### Create

```ruby
# Method 1: Create and save in one step
post = Post.create(title: "Hello World", body: "My first post")

# Method 2: Create, then save separately
post = Post.new(title: "Hello World")
post.body = "My first post"
post.save
```

### Read

```ruby
# Get all posts
Post.all

# Get one post by its id
Post.find(1)

# Get the first post
Post.first

# Get the last post
Post.last

# Find by a specific field
Post.find_by(title: "Hello World")

# Find multiple
Post.find_by(title: "Hello World", author: "Alice")
```

### Query Methods

```ruby
# Where (filter)
Post.where(published: true)
Post.where("created_at > ?", 1.week.ago)
Post.where(author: "Alice").where(published: true)

# Order
Post.order(created_at: :desc)
Post.order(title: :asc)

# Limit and offset
Post.limit(5)
Post.limit(5).offset(10)  # Skip 10, get 5

# Combine them
Post.where(published: true)
    .order(created_at: :desc)
    .limit(10)

# Count
Post.count
Post.where(author: "Alice").count
```

### Update

```ruby
# Method 1: Find and update
post = Post.find(1)
post.update(title: "Updated Title", body: "New content")

# Method 2: Update in place
post = Post.find(1)
post.title = "New Title"
post.save

# Method 3: Update all matching records
Post.where(author: "Alice").update_all(author: "Bob")
```

### Delete

```ruby
# Delete one record
post = Post.find(1)
post.destroy

# Delete by condition
Post.where(published: false).destroy_all

# Delete all
Post.destroy_all
```

**Important:** `destroy` runs callbacks (like deleting associated records), while `delete` does not. Use `destroy` unless you know what you are doing.

## Scopes

Scopes let you define common queries in your model so you can reuse them:

```ruby
class Post < ApplicationRecord
  scope :published, -> { where(published: true) }
  scope :recent, -> { order(created_at: :desc).limit(5) }
  scope :by_author, ->(name) { where(author: name) }
end
```

Then use them like this:

```ruby
Post.published
Post.recent
Post.by_author("Alice")
Post.published.by_author("Alice")
```

Scopes keep your code clean and make your queries read like English.

## Playing with Your Data

Rails gives you a console where you can try all of this interactively:

```bash
rails console
```

Then type Ruby code and see the results immediately:

```ruby
> Post.count
=> 0

> Post.create(title: "Hello", body: "World")
=> #<Post id: 1, title: "Hello", ...>

> Post.count
=> 1

> Post.first.title
=> "Hello"
```

This is the best way to learn Active Record. Try things in the console before putting them in your code.

## How Rails Models Compare to .NET Terms

If you come from .NET, the naming can be confusing. In ASP.NET you might have separate classes for Entity, DTO, and ViewModel. In Rails, the **Model** does all of those jobs.

| .NET Concept | What It Does | Rails Equivalent |
|---|---|---|
| **Entity** (e.g., `PostEntity`) | Maps to a database table, one property per column | **Model** (`app/models/post.rb`) — the same thing. No separate entity class needed. |
| **DbContext** with `DbSet<Post>` | The bridge between your code and the database | **Active Record** — built into every model. `Post.all`, `Post.find(1)` talk to the database directly. |
| **DTO** (e.g., `PostDto`) | A simplified class that carries only the data a specific API or view needs | **Not a separate thing.** Just use the model. If you need different data, add a method or scope to the model. |
| **ViewModel** (e.g., `PostViewModel`) | A class shaped specifically for what a view needs | **Also the model.** You pass `@post` or `@posts` directly to the view. If the view needs extra data, use a `before_action` or a helper. |
| **Migration** (manual SQL scripts) | Changes to the database schema over time | **Migration** (`db/migrate/`) — same concept, but in Ruby and automated with `rails db:migrate` |
| **Repository pattern** (`IPostRepository`) | A layer that hides database access behind an interface | **Not used.** Active Record IS the repository. `Post.where(...)` is already your data access layer. |

### In Practice

**In .NET**, you might write something like this to send data from the database to the view:

```csharp
// Entity
public class PostEntity {
    public int Id { get; set; }
    public string Title { get; set; }
    public string Body { get; set; }
    public DateTime CreatedAt { get; set; }
}

// DTO (to avoid sending too much data)
public class PostDto {
    public string Title { get; set; }
    public string Excerpt { get; set; }
}

// In the controller
public IActionResult Index() {
    var entities = _dbContext.Posts.ToList();
    var dtos = entities.Select(e => new PostDto {
        Title = e.Title,
        Excerpt = e.Body.Length > 100 ? e.Body[..100] + "..." : e.Body
    });
    return View(dtos); // View expects a list of PostDto
}
```

**In Rails**, the same thing is much shorter:

```ruby
# app/models/post.rb — this IS your entity and your "dto"
class Post < ApplicationRecord
  scope :published, -> { where(published: true) }
end

# app/controllers/posts_controller.rb
def index
  @posts = Post.published  # @posts is the model itself, used directly in the view
end
```

```erb
<!-- app/views/posts/index.html.erb — the view uses @posts directly -->
<% @posts.each do |post| %>
  <h2><%= post.title %></h2>
  <p><%= post.body.truncate(100) %></p>
<% end %>
```

If you need to shape the data differently (like a DTO), you do not create a new class. You just add a method to the model:

```ruby
class Post < ApplicationRecord
  def excerpt
    body.truncate(100)
  end
end
```

Then in the view: `<%= post.excerpt %>`.

### The Key Takeaway

In Rails, the **Model** is everything. It is your Entity (maps to the database), your data access layer (Active Record handles queries), and the object you pass to your views. There is no separate DTO or ViewModel. If you need to transform the data, you add a method to the model rather than creating a whole new class.

This feels like less files, less boilerplate, and less jumping between classes to understand what is happening.

## Active Record vs Entity Framework

Both Active Record and Entity Framework are ORMs (Object-Relational Mappers). They both convert database rows into objects you can use in your code. But they have different philosophies.

| Concept | Entity Framework (.NET) | Active Record (Rails) |
|---|---|---|
| **Setup** | You manually create a `DbContext` class, define `DbSet<T>` properties, configure connections in `appsettings.json` | You run `rails generate model Post title:string`. Rails creates the model, migration, and everything auto-wires through naming conventions. |
| **Migrations** | `Add-Migration CreatePosts` then `Update-Database` | `rails generate model Post ...` then `rails db:migrate` |
| **Query syntax** | LINQ: `_context.Posts.Where(p => p.Published).OrderBy(p => p.CreatedAt)` | Active Record: `Post.where(published: true).order(created_at: :desc)` |
| **Loading related data** | `.Include(p => p.Comments)` (eager loading) or `.ThenInclude()` for nested | `.includes(:comments)` (eager loading) or just call `post.comments` (lazy loading by default) |
| **Saving to DB** | `_context.SaveChanges()` after modifying entities | `post.save` directly on the object |
| **Tracking changes** | `DbContext` tracks changes to entities. You modify properties and call `SaveChanges`. | The model itself tracks changes. You modify attributes and call `save`. |
| **Database first** | Reverse-engineer models from an existing database (`Scaffold-DbContext`) | `rails db:models` or use `annotate` gem, but less common — Rails is usually code-first |
| **Convention** | Convention over configuration exists but you often need `[Table]`, `[Column]`, `[Key]` attributes or fluent API config | Convention over configuration is stronger. A `Post` model automatically maps to the `posts` table, `id` column is the primary key, `created_at`/`updated_at` are automatic. |
| **Raw SQL** | `_context.Database.SqlQueryRaw<Post>("SELECT * FROM posts")` | `Post.find_by_sql("SELECT * FROM posts")` |
| **Explicit interface** | Often paired with a repository interface (`IPostRepository`) for unit testing | No repository interface by default. You query `Post.where(...)` directly. Testing uses the database or mocking. |

### Code Comparison: Same Query in Both

**Query:** Get the 10 most recent published posts with their comments.

**Entity Framework:**
```csharp
// You need DbContext, Entity classes, and often a DTO
public class PostEntity {
    public int Id { get; set; }
    public string Title { get; set; }
    public string Body { get; set; }
    public bool Published { get; set; }
    public DateTime CreatedAt { get; set; }
    public List<CommentEntity> Comments { get; set; }
}

public class PostDto {
    public string Title { get; set; }
    public int CommentCount { get; set; }
}

// In your controller
public async Task<IActionResult> Index() {
    var posts = await _context.Posts
        .Include(p => p.Comments)
        .Where(p => p.Published)
        .OrderByDescending(p => p.CreatedAt)
        .Take(10)
        .Select(p => new PostDto {
            Title = p.Title,
            CommentCount = p.Comments.Count
        })
        .ToListAsync();

    return View(posts);
}
```

**Active Record:**
```ruby
# The model itself is already your entity — no separate class needed
class Post < ApplicationRecord
  scope :published, -> { where(published: true) }
  scope :recent, -> { order(created_at: :desc) }
end

# In your controller
def index
  @posts = Post.published.recent.includes(:comments).limit(10)
end
```

```erb
<% @posts.each do |post| %>
  <h2><%= post.title %></h2>
  <p><%= pluralize(post.comments.count, "comment") %></p>
<% end %>
```

### What This Means For You

- **Less code.** Active Record needs fewer files and less configuration than Entity Framework. One model file replaces Entity + DbSet + often DTO.
- **Queries read like English.** `Post.where(published: true).order(created_at: :desc)` reads naturally. No lambda expressions or LINQ syntax to learn.
- **No `SaveChanges()` call.** Calling `post.save` on the model directly persists to the database. There is no separate `DbContext` to manage.
- **No repository pattern.** Active Record follows the "active record pattern" where the object itself handles database operations. You do not wrap it in a repository interface unless you have a specific reason to.
