# Associations and Validations

When you build a real app, your data is connected. A user has posts. A post has comments. A comment belongs to a user. These connections are called **associations** in Rails.

## Why Associations Matter

Without associations, you would have to do everything manually:

```ruby
# Without associations (painful)
user = User.find(1)
posts = Post.where(user_id: user.id)

# With associations (beautiful)
user = User.find(1)
posts = user.posts
```

Associations make your code read like plain English and save you from writing the same queries over and over.

## The Main Types

### belongs_to

Use this when one record belongs to another:

```ruby
class Post < ApplicationRecord
  belongs_to :user
end

class Comment < ApplicationRecord
  belongs_to :post
  belongs_to :user
end
```

The table that has `belongs_to` needs a column with the other table's id. For `belongs_to :user` the `posts` table needs a `user_id` column, and the `comments` table also needs a `user_id` column.

### has_many

Use this when one record has many of another:

```ruby
class User < ApplicationRecord
  has_many :posts
  has_many :comments
end

class Post < ApplicationRecord
  belongs_to :user
  has_many :comments
end
```

Now you can do:

```ruby
user = User.find(1)
user.posts           # Returns all posts by this user
user.comments        # Returns all comments by this user

post = Post.find(1)
post.comments        # Returns all comments on this post
post.user            # Returns the user who wrote this post
```

### has_one

Use this when one record has exactly one of another:

```ruby
class User < ApplicationRecord
  has_one :profile
end

class Profile < ApplicationRecord
  belongs_to :user
end
```

This lets you do `user.profile`.

### dependent: :destroy

When you delete a user, you probably want to delete their posts too:

```ruby
class User < ApplicationRecord
  has_many :posts, dependent: :destroy
end
```

Now if you do `user.destroy`, Rails will automatically destroy all that user's posts too. Without this, those posts would stay in your database with a `user_id` that points to nothing (orphan records).

## Migrations for Associations

When you add an association, you need a column for the foreign key:

```bash
rails generate migration AddUserToPosts user:references
```

This creates a migration that adds `user_id` to the posts table and sets up an index. Run `rails db:migrate` to apply it.

## Validations: Keeping Data Clean

Rails gives you **two layers** of data protection. Think of them as a bouncer at the door (application layer) and a locked vault (database layer). Both exist for different reasons and you should use both.

### Application-Level Validations (Model Layer)

These live in your model file (`app/models/post.rb`). They run **before** the SQL query hits the database. If validation fails, Rails never sends the INSERT/UPDATE to the database. This is your first line of defense.

```ruby
class Post < ApplicationRecord
  belongs_to :user
  has_many :comments, dependent: :destroy

  validates :title, presence: true
  validates :title, length: { in: 5..100 }
  validates :body, presence: true
  validates :author_email, format: { with: /\A[^@\s]+@[^@\s]+\z/ }
end
```

### Common Application Validations

```ruby
class User < ApplicationRecord
  # Field must exist (not nil, not empty string)
  validates :name, presence: true

  # Field must be unique across all records
  validates :email, presence: true, uniqueness: true

  # Field must be at least 6 characters
  validates :password, length: { minimum: 6 }

  # Field must be a number and greater than 0
  validates :age, numericality: { greater_than: 0 }

  # Field must be one of the allowed values
  validates :role, inclusion: { in: %w[admin member guest] }

  # Field must match a pattern
  validates :slug, format: { with: /\A[a-z0-9-]+\z/, message: "only lowercase letters, numbers, and dashes" }
end
```

These validations are **Ruby code** — they run in the application process. They give you nice error messages for users and prevent bad data from even attempting to reach the database.

### Database-Level Constraints (Migration Layer)

These live in your migration files (`db/migrate/...`). They are enforced **inside the database itself**, at the SQL level. Even if your app has a bug or someone inserts data directly, the database will reject bad data.

```ruby
# db/migrate/20240101000001_create_posts.rb
class CreatePosts < ActiveRecord::Migration[7.0]
  def change
    create_table :posts do |t|
      t.string :title, null: false                    # Cannot be NULL in the database
      t.text :body, null: false                       # Cannot be NULL
      t.string :author_email                          # Can be NULL (no null: false)
      t.boolean :published, default: false            # Default value if not provided
      t.integer :position, default: 0                 # Defaults to 0
      t.timestamps
    end

    # Unique index — database will reject duplicates
    add_index :posts, :author_email, unique: true
  end
end
```

### Common Database Constraints

```ruby
# In your migration, inside create_table or add_column:

# NOT NULL — column cannot be empty
t.string :title, null: false

# Default value — fills in automatically if not provided
t.integer :views_count, default: 0
t.boolean :published, default: false

# Unique index — prevents duplicate values at the database level
add_index :users, :email, unique: true

# Unique index on two columns together (e.g., one vote per user per post)
add_index :votes, [:user_id, :post_id], unique: true

# Foreign key — ensures the referenced record exists (Rails adds this automatically with references)
t.references :user, null: false, foreign_key: true

# Limit on string length
t.string :title, limit: 100
```

You can also add constraints to an **existing** table with a migration:

```bash
rails g migration AddNullFalseToPostsTitle
```

```ruby
class AddNullFalseToPostsTitle < ActiveRecord::Migration[7.0]
  def change
    change_column_null :posts, :title, false
  end
end
```

### Application vs Database: Which One to Use?

Both layers exist for different reasons:

| Concern | Application Validations | Database Constraints |
|---|---|---|
| **When it runs** | Before the SQL query, in Ruby | During the SQL query, inside the database |
| **Error messages** | Friendly, user-facing (`"Title can't be blank"`) | Generic SQL errors, not meant for users |
| **Enforcement** | Only if data goes through your Rails app | Always — even direct SQL or another app |
| **Performance** | Fast (no DB round-trip for simple checks) | Can be faster for uniqueness checks (indexed) |
| **What it catches** | Format, length, custom business rules | Null values, duplicates, referential integrity |

### The Problem with Only Application Validations

```ruby
# app/models/post.rb
class Post < ApplicationRecord
  validates :title, presence: true
end
```

This works **most** of the time. But what happens when:
- A developer runs `Post.create!(title: nil)` in the Rails console (skips validation with `!`?)
- Another service writes directly to the database
- A migration adds rows without going through the model
- Two requests hit the server at the same time — both pass `uniqueness` validation before either saves (race condition)

### The Fix: Use Both Layers

```ruby
# Migration — database won't accept NULL titles or duplicate emails
class CreateUsers < ActiveRecord::Migration[7.0]
  def change
    create_table :users do |t|
      t.string :name, null: false
      t.string :email, null: false
      t.timestamps
    end
    add_index :users, :email, unique: true
  end
end
```

```ruby
# Model — gives users nice error messages
class User < ApplicationRecord
  validates :name, presence: true
  validates :email, presence: true, uniqueness: true
end
```

Now you get:
1. **Friendly messages** when a user forgets to fill in a field (application validation)
2. **Safety net** if something bypasses your model (database constraint)
3. **Race condition protection** for uniqueness — the database index guarantees it

**Rule of thumb:** Always add `null: false` and `unique: true` (where appropriate) in migrations, AND add corresponding `validates` in the model. The database constraint is your safety net; the model validation is your user-friendly gatekeeper.

### What Happens When Validation Fails

When you try to save an invalid record, Rails returns `false`:

```ruby
post = Post.new(title: "")  # Title is empty, validation will fail
post.save                   # Returns false
post.valid?                 # Returns false
```

### Inspecting Errors

When a record is invalid, Rails stores error details in the `.errors` object. Here are the most common ways to inspect them:

```ruby
post = Post.new(title: "", body: nil)
post.valid?

# Are there any errors at all?
post.errors.any?                    # => true

# How many errors?
post.errors.count                   # => 2

# Full sentences — great for showing to users
post.errors.full_messages
# => ["Title can't be blank", "Body can't be blank"]

# Errors grouped by field name
post.errors.messages
# => {:title => ["can't be blank"], :body => ["can't be blank"]}

# Errors for one specific field
post.errors[:title]
# => ["can't be blank"]

# The first error message for a field
post.errors.first_for(:title)  # (Rails 7.1+)
# or just:
post.errors[:title].first
# => "can't be blank"

# Detailed error objects (field, message, type)
post.errors.details
# => {:title => [{:error => :blank}], :body => [{:error => :blank}]}

# Check if a specific field has an error
post.errors[:title].any?            # => true
```

### Using Errors in a Controller

In your controller, you use this to decide what to do:

```ruby
def create
  @post = Post.new(post_params)

  if @post.save
    # If validation passed, show the post
    redirect_to @post
  else
    # If validation failed, show the form again with errors
    render :new
  end
end
```

And in your view, Rails automatically shows errors next to fields:

```erb
<%= form_with model: @post do |form| %>
  <% if @post.errors.any? %>
    <div id="error_explanation">
      <h2><%= pluralize(@post.errors.count, "error") %> stopped this post from being saved:</h2>
      <ul>
        <% @post.errors.full_messages.each do |msg| %>
          <li><%= msg %></li>
        <% end %>
      </ul>
    </div>
  <% end %>

  <div>
    <%= form.label :title %>
    <%= form.text_field :title %>
  </div>
  <!-- ... -->
<% end %>
```

## Callbacks: Code That Runs Automatically

Callbacks are methods that run at certain points in a model's lifecycle — before or after saving, creating, updating, or validating. Think of them as "hooks" that let you run extra code automatically.

### The Most Common Callbacks

```ruby
class Post < ApplicationRecord
  belongs_to :user
  has_many :comments, dependent: :destroy

  validates :title, presence: true

  # Runs before validations run
  before_validation :set_default_title

  # Runs before saving (both create and update)
  before_save :sanitize_title

  private

  def set_default_title
    self.title ||= "Untitled"
  end

  def sanitize_title
    self.title = title.strip
  end
end
```

**Order of operations when you call `post.save`:**

1. `before_validation` runs
2. Validations run
3. `after_validation` runs
4. `before_save` runs
5. SQL INSERT/UPDATE runs
6. `after_save` runs

### Callback Examples with the Blog

```ruby
class Post < ApplicationRecord
  belongs_to :user
  has_many :comments, dependent: :destroy

  validates :title, presence: true
  validates :body, presence: true

  # Before validation: set a fallback value
  before_validation :set_default_title

  # Before save: clean up data
  before_save :downcase_slug

  # After create: log or notify (no rollback possible here)
  after_create :log_post_created

  # Before create: set a value only on first save
  before_create :set_published_at

  private

  def set_default_title
    self.title ||= "Untitled Post"
  end

  def downcase_slug
    self.slug = slug.downcase if slug.present?
  end

  def log_post_created
    Rails.logger.info "Post ##{id} was created"
  end

  def set_published_at
    self.published_at = Time.current
  end
end
```

### Callbacks Can Abort the Save

If a `before_` callback calls `throw :abort`, the save stops and Rails treats it like a failed validation:

```ruby
class Comment < ApplicationRecord
  belongs_to :post

  before_save :check_spam

  private

  def check_spam
    if body.include?("buy now")
      errors.add(:body, "looks like spam")
      throw :abort  # Stops the save and returns false
    end
  end
end
```

Now `comment.save` returns `false` and `comment.errors.full_messages` includes the spam message.

### When to Use Callbacks vs Validations

| Situation | Use |
|---|---|
| Checking if data is valid (e.g., "title must be present") | `validates` |
| Setting a default value before checking validity | `before_validation` |
| Cleaning or formatting data before saving | `before_save` |
| Performing side effects after saving (e.g., send email, log) | `after_create` / `after_save` |
| Preventing a save based on a condition | `before_save` with `throw :abort` |

**Rule of thumb:** Use validations for data correctness. Use callbacks for automation (set defaults, clean input, trigger side effects).

Here is a complete example of models working together:

```ruby
# app/models/user.rb
class User < ApplicationRecord
  has_many :posts, dependent: :destroy
  has_many :comments, dependent: :destroy

  validates :name, presence: true
  validates :email, presence: true, uniqueness: true
end

# app/models/post.rb
class Post < ApplicationRecord
  belongs_to :user
  has_many :comments, dependent: :destroy

  validates :title, presence: true, length: { minimum: 5 }
  validates :body, presence: true
end

# app/models/comment.rb
class Comment < ApplicationRecord
  belongs_to :post
  belongs_to :user

  validates :body, presence: true
end
```

With this setup, you can navigate your data naturally:

```ruby
# Find a user and see their posts
alice = User.find_by(name: "Alice")
alice.posts.each do |post|
  puts post.title
  post.comments.each do |comment|
    puts "  - #{comment.body}"
  end
end
```
